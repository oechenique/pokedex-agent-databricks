**Hallazgo real + fix -- timeout explícito en `mcp_client.py` (2026-09-20).** Primer test contra `/api/chat` en producción: la Databricks App estaba dormida, y el request se colgó en silencio más de 100s (probado con curl y con PowerShell/.NET, dos stacks TLS distintos, mismo resultado) -- ni error, ni timeout, ni respuesta. Causa: `create_mcp_http_client()` en `mcp_client.py` no tenía `timeout` configurado, así que un cuelgue de red (Databricks App dormida/redeployando) bloqueaba el `await` para siempre en vez de fallar rápido. Costó ~15 minutos distinguir esto de un error de auth M2M mal seteado, porque el síntoma (nada de respuesta) es idéntico al de una credencial mal configurada colgada en un retry silencioso. **Fix aplicado:** `_HTTP_TIMEOUT = httpx2.Timeout(15.0, connect=5.0)` pasado a `create_mcp_http_client(headers=headers, timeout=_HTTP_TIMEOUT)` -- `httpx2`, no el `httpx` clásico, porque `mcp>=2.1.1` migró a ese paquete sucesor (agregado como dependencia explícita en `agent/requirements.txt` y `pyproject.toml`, antes solo llegaba transitivo). Con esto, un cuelgue de red futuro tira `httpx2.ConnectTimeout`/`ReadTimeout` en segundos, no un cuelgue silencioso de minutos.

**Hallazgo real + fix -- `DATABRICKS_HOST` separado del host de la app (2026-09-20).** Con la Databricks App ya `RUNNING`, el segundo test a `/api/chat` respondió rápido (~1s) pero con `500 Internal Server Error`. Traceback real de los Runtime Logs de Vercel: `mcp_client.py` usaba `Config(host=config.MCP_SERVER_URL)` para autenticar Y como destino -- pero el host de una Databricks App no expone el endpoint de descubrimiento OIDC (`<host>/oidc/.well-known/oauth-authorization-server`) que necesita el OAuth M2M con `client_id`/`client_secret`; hace falta el host del WORKSPACE para eso. Confirmado contra la doc oficial (no se adivinó el fix): [Connect to an API Databricks app using token authentication](https://docs.databricks.com/gcp/en/dev-tools/databricks-apps/connect-local) -- el patrón documentado es `WorkspaceClient(host=<workspace-url>, client_id=..., client_secret=...).config.authenticate()` para conseguir el token, y ESE token (`Authorization: Bearer`) se manda igual a la URL de la app para las llamadas reales. **Fix:** nueva env var `DATABRICKS_HOST` (`agent/config.py`) con el host del workspace (`https://adb-7405616363788532.12.azuredatabricks.net`), usada solo para construir el `Config` de `_auth_headers()` (`auth_host = config.DATABRICKS_HOST or config.MCP_SERVER_URL`); `MCP_SERVER_URL` sigue siendo el único destino real de las llamadas MCP (`streamable_http_client`), sin cambios ahí. En local con perfil OAuth (`DATABRICKS_PROFILE`) no hace falta `DATABRICKS_HOST` -- el perfil ya trae su propio host cacheado en `~/.databrickscfg`, sigue andando igual que antes.

**Confirmado -- `CAN_USE` faltante sobre la app (2026-09-20).** Como se sospechaba: Databricks Apps tiene su propio control de acceso a nivel app (separado de los grants de Unity Catalog), y `backend_m2m` no lo tenía. Fix: `databricks_permissions.backend_m2m_app_use` en `permissions.tf` (`app_name = databricks_app.mcp_server.name`, `permission_level = "CAN_USE"` -- confirmado contra la doc oficial del provider, `terraform-provider-databricks/docs/resources/permissions.md`, antes de escribirlo). Apply targeteado, 1 recurso agregado. Esto cambió el síntoma de 500/cuelgue a un 401 explícito -- progreso real, pero no cerró el caso (ver bloqueo de abajo).

**Estado: bloqueado, no fallido.** La arquitectura y el código están probados correctos -- lo que no funciona es la propagación/enforcement de un permiso del lado de Databricks, algo fuera de este repo. **Descartado con evidencia, en este orden:**
1. Nombres de env vars en Vercel -- comparados letra por letra contra `grep os.environ.get` de `agent/config.py` y `backend/app.py`, más lo que lee el SDK de Databricks por su cuenta (`DATABRICKS_CLIENT_ID`/`SECRET`, confirmado en `databricks/sdk/config.py:125-126`) y la librería `anthropic` (`ANTHROPIC_API_KEY`). Sin typos, `DATABRICKS_PROFILE` correctamente ausente.
2. IP Access List en el workspace -- `databricks ip-access-lists list --profile adb-7405616363788532 -o json` devuelve `[]`, no hay ninguna activa.
3. Audience/token-exchange (RFC 8693) -- probado a mano contra `/oidc/v1/token`: pedir `audience=<oauth2_app_client_id>` sobre un token ya emitido da `400 invalid_request: "audience parameter is not supported for access_token"`. No es el mecanismo correcto para este caso.
4. Caching de `Config`/token a nivel módulo en `mcp_client.py` o en `create_mcp_http_client()` -- código leído línea por línea, ambos construyen todo fresco por llamada/request, sin ningún singleton ni variable de módulo. Confirmado también que un redeploy manual (cold start garantizado) no cambia el resultado.
5. **Header `Authorization` mal armado o vacío** -- logueado en vivo (`DEBUG headers keys=['Authorization']`, prefijo `Bearer` correcto, largo esperado).
6. **JWT con claims incorrectos** (`aud`/`scope`/`iss` distintos entre Vercel y local) -- decodificado el payload (sin verificar firma) en una repro local *correctamente aislada* (ver hallazgo metodológico abajo): `sub` = client_id del SP (correcto), `aud=['7405616363788532']`, `scope='all-apis'`, `iss` = el workspace correcto. El token está perfecto.
7. **`CAN_USE` mal configurado o revertido** -- confirmado con `databricks permissions get apps pokedex-mcp-server --profile adb-7405616363788532 -o json`: `backend_m2m` tiene `CAN_USE`, `inherited: false`, directo sobre el recurso. El ACL es correcto ahora mismo, vía API, no solo en el estado de Terraform.

**Hallazgo metodológico importante (para no repetir el error):** el primer intento de reproducir esto en local con las credenciales M2M dio un falso "funciona" -- el `Config(profile=None, host=...)` cayó igual al perfil OAuth cacheado en `~/.databrickscfg` de esta máquina (mismo host que un profile ya logueado), autenticando como el usuario humano (`kukkiibakeryco@gmail.com`) en vez de como el service principal. Se detectó recién al decodificar el JWT y ver el `sub` equivocado. Para forzar M2M real en una repro local hace falta `DATABRICKS_CONFIG_FILE=<ruta inexistente>` (o cualquier mecanismo que garantice que no hay `~/.databrickscfg` visible), no alcanza con pasar `client_id`/`client_secret` por env var si hay un profile cacheado para el mismo host.

**Reproducido 100% fuera de Vercel** (aislando código/librería `mcp`/backend por completo): un POST crudo con `requests` (JSON-RPC `initialize`, sin la librería `mcp`) y un GET plano a `${MCP_SERVER_URL}/mcp`, ambos con un token M2M fresco recién emitido, devuelven `401` con el mismo body vacío. Un intento aislado anterior con esencialmente el mismo tipo de request dio `200` en un momento puntual, sin que cambiara nada de nuestro lado entre uno y otro.

**Hipótesis final (sin código nuestro que la resuelva):** propagación o caché inconsistente en la capa de *enforcement* de Databricks Apps (la que efectivamente valida el permiso al servir la app) -- distinta de la capa de control/API que ya confirma el ACL correcto al toque. El `200` aislado sugiere que a veces sí propaga; la mayoría de los intentos, no. No se sabe cuánto puede tardar en asentarse (¿minutos? ¿horas?) ni si es un límite/bug de una feature relativamente nueva (M2M service principal invocando una Databricks App programáticamente).

**Siguiente paso concreto (próxima sesión, no ahora):** reintentar el script de repro aislado (`DATABRICKS_CONFIG_FILE` a una ruta inexistente + POST crudo a `${MCP_SERVER_URL}/mcp`) después de una espera larga sin actividad (horas, no minutos) antes de seguir generando tráfico contra el endpoint.
